# Google Forms AI Grader

教師がスプレッドシートだけを操作して、Googleフォーム試験の生成から採点までを行う仕組みです。
仕様は `docs/DESIGN_SPEC.md`（変更は `docs/DESIGN_ADDENDUM.md` を優先）、用語は `CONTEXT.md`、決定の理由は `docs/adr/` にあります。

- テスト: `npm test`（Google の環境は不要。依存パッケージなし）。純粋ロジックの単体テストに加え、`tests/gasFlow.test.js` が偽の Google（メモリ上のシート・フォーム）で、セットアップから採点・書き戻しまでを通しで動かします。これは実環境の代わりにはなりません
- 実際の Google 環境での確認は、2026-10-20 に一部だけ行いました（セットアップ、フォーム生成、AUTO 採点、MANUAL の確定と書き戻し）。LLM による採点は、API キーが無いため未確認です。下の **【未確認】** の項目を、導入担当者が確認してください

## 教師の使い方（導入後）

先生が触るのは「試験作成」シートだけです。結果は「結果」シートで見ます。ほかのシートは裏方として隠してあります。

1. 試験作成シートの表（11行目から）に、1行1問で書く
   - 掲載: フォームに載せるならチェック
   - 問題文、種類（短答・数値・記述・選択・複数選択・プルダウン）、配点
   - 正答: 記述は模範解答（空欄可）
   - 別解: 短答で、ほかに正解とする答え（`||` 区切り）。数値は許容差
   - 選択肢: 選択式のとき（`||` 区切り）
   - 採点の観点: 記述のとき、何が書けていれば何点か
   - 必須: 回答を必須にするならチェック
   - 書き始めた行で、まだ埋めていない必須の欄は黄色になる
2. フォームのタイトルと説明を、上の欄に書く
3. 「これでOK」にチェックを入れる。不備があれば、メッセージ欄に問題番号（種類の誤りは行番号）つきで出る
4. 配る前に、フォームの設定で成績の公開を「後で」にする。フォームURL欄のリンクを学生に配る
5. 選択式・短答・数値は自動で採点される（約1分ごと）。記述は、Claude に「採点して」と頼む（`docs/GRADING_BY_CLAUDE.md`）
6. メニュー「AI Grader」→「手動採点を反映」を押すと、確定した回答の点数がフォームに付く

フォームの先頭には、必須の「氏名（Name）」欄が自動で入ります。回答は1人1回に制限されるため、学生は Google アカウントでログインして回答します。回答はどの言語でも構いません。短答・数値の誤答は、その場で0点になります。ただし、正答と違う文字（英字・ハングルなど）で書かれた回答だけは、別の言語で正しく答えている可能性があるため、Claude が意味を確かめてから点を付けます。中国語の簡体字のように日本語と同じ漢字で書かれた別言語の正答を認めたいときは、「別解」に書き足してください。

問題の追加は空いている行に書くだけ、取り下げは「掲載」を外すだけ、順番は行を並べ替えるだけです。問題番号は表の右端に自動で付き、行と一緒に動きます。

困ったときは、メニュー「AI Grader」→「システム診断」で状態を、試験作成シートのメッセージ欄に表示できます。

## 導入手順（導入担当者向け）

1. 空のスプレッドシートを作り、「拡張機能 > Apps Script」を開いて、プロジェクトの設定からスクリプトIDを控える
2. このリポジトリで `npm install -g @google/clasp`、`clasp login`、`cp .clasp.json.example .clasp.json`（スクリプトIDを書く）、`clasp push`
3. スプレッドシートを開き直し、メニュー「AI Grader > 初期セットアップ」を実行して権限を許可する
4. LLM 採点を使うなら、次の「LLM 採点の準備」をする
5. 受付ページ（学生ごとに数字違いの資料を配る）を使うなら、次の「受付ページの準備」をする

### 受付ページの準備（使う場合だけ）

受付ページは、採点の仕組みとは別の Apps Script プロジェクト（`reception/`）です。誰でも開けるページなので、採点の仕組みの関数を外から呼ばれないよう分けてあります（ADR 0009）。受付ページは数字違いの資料を配るテストのときだけ使い、集計表のテスト一覧で印の付いたテストへ案内します（ADR 0012）。学生に配る受付ページの URL は毎回同じです。先に、下の「集計表の導入」を済ませておきます。

1. 受付ページを使うテストのスプレッドシートで、名簿シート（クラス・No.・氏名・呼び名）と資料シート（資料番号・本文と、採点用の家賃〜開始期限。資料番号は1から欠番なし）を埋め、初期セットアップをやり直す
2. `reception/LocalSettings.example.js` を `reception/LocalSettings.js` に写し、**集計表**のスプレッドシートの ID を `GRADEBOOK_ID` に書く（GitHub には置かない。テストごとに書き換えない）
3. `reception/` で `clasp create --type standalone --title 受付ページ --rootDir .` を1回だけ実行する（`appsscript.json` が上書きされたら元に戻す）。できた `reception/.clasp.json` は GitHub に置かれないので、次に新しい ZIP を展開したときは前回のフォルダから写す
4. **`reception/.clasp.json` があることを確かめてから** `reception/` で `clasp push` する。無いまま打つと、clasp が上のフォルダの設定を拾い、採点の仕組みのプロジェクトを受付ページのコードで上書きしてしまう
5. 初回は `clasp deploy`。出てきたデプロイ ID から `https://script.google.com/macros/s/<デプロイID>/exec` を作り、デプロイ ID は引き継ぎメモに残す（忘れたら `clasp deployments` で見られる）
6. そのURLを先生が一度開き、権限を許可する（許可の画面が出なければ、受付ページのプロジェクトのエディタで `getReceptionRoster` を1回実行する）。その後で学生に配る（学生以外には配らない。名簿の氏名が見えるため）
7. コードを直したときは `clasp push` のあと `clasp deploy -i <同じデプロイID>` を使う（`-i` なしでは URL が変わり、`push` だけでは公開中のページは古いまま）
8. URL を配ったあとは、名簿のクラスを変えない（変えて「これでOK」を押すと新しい版のフォームになり、受付ページの入口がそちらに切り替わる）
9. テストのたびに、集計表のテスト一覧で、そのテストの行の「受付ページを使う」と「実施中」に印を付ける（右端のスプレッドシートのIDが空なら、メニュー「集計表 > 取り込む」を1回押すと埋まる）。終わったテストの「実施中」は外す。両方に印の付いた行がちょうど1つでないと、受付ページは「受付の準備ができていません。先生に連絡してください」と出す。印を付け替えてから受付ページが切り替わるまで、1分ほどかかる

Apps Script エディタでコードを直接直さないでください（正本は GitHub です。これは運用上の約束で、技術的に強制されてはいません）。

### 集計表の導入

集計表は、全科目・全テストの合計点を学生1人1行・テスト1回1列で並べる、1つのスプレッドシートです。採点の仕組み・受付ページとは別の Apps Script プロジェクト（`gradebook/`）で、各テストの結果を集計表の側から吸い上げます（ADR 0010）。

1. 空のスプレッドシートを作り（名前は「集計表」など）、「拡張機能 > Apps Script」を開いて、プロジェクトの設定からスクリプトIDを控える
2. `gradebook/.clasp.json.example` を `gradebook/.clasp.json` に写し、スクリプトIDを書く（GitHub には置かれないので、次に新しい ZIP を展開したときは前回のフォルダから写す）
3. **`gradebook/.clasp.json` があることを確かめてから** `gradebook/` で `clasp push` する。無いまま打つと、clasp が上のフォルダの設定を拾い、採点の仕組みのプロジェクトを集計表のコードで上書きしてしまう
4. 集計表を開き直し、メニュー「集計表 > 初期セットアップ」を押して権限を許可する。名簿・テスト一覧・成績・要確認のシートができる（裏方の取り込み記録・集計表の設定は隠してある）。何度押しても、入れたものは消えない
5. 名簿シートに、1人1行で氏名・クラス・アカウント（学生の Google アカウントのメールアドレス）を入れる。同じ学生が使ったことのある別のアカウントや別の綴りは、別のアカウント・別の綴りの欄に `||` 区切りで書く。右端の学生番号は空けておく（初期セットアップか取り込みのときに自動で振られ、その後は変わらない。書き換えない）
6. テスト一覧シートに、テスト名・科目・実施日・テストのスプレッドシートのURLを書く
7. メニュー「集計表 > 取り込む」を押すと、確定した回答の合計点が成績シートに並ぶ。照合できない回答と2回送信は要確認シートに出るので、「この学生にする」に学生番号を書くか、使う回答の「この回答を使う」にチェックを入れて、もう一度「取り込む」を押す。「この学生にする」で結びつけた回答のアカウントや氏名の綴りが、その学生の名簿に無ければ、別のアカウント・別の綴りに自動で足される（次のテストからは自動で照合される）

成績シートは取り込みのたびに作り直されるので、書き込まないでください。空欄の理由は「（未確定）」「（要確認）」「（選択待ち）」で示します。

#### ひな型の用意（導入担当者が1回だけ）

テストは1回ごとに、ひな型のスプレッドシートをコピーして作ります（ADR 0010）。

1. 空のスプレッドシートを作り（名前は「ひな型」など）、「拡張機能 > Apps Script」のプロジェクトの設定からスクリプトIDを控える
2. このリポジトリの `.clasp.json`（`src/` の送り先）のスクリプトIDを、ひな型のものにして `clasp push` する。以後、仕組みを直したらひな型へ送る（次に作るテストから反映される。作り終えたテストは、コピーした時点の仕組みのまま）
3. **ひな型では初期セットアップを押さない**（押すと1分ごとの自動処理がひな型で動き出す）。ひな型に Settings シートがある場合は、`COLLECT_EMAIL` を TRUE にしておく（無ければ、新しいテストで初期セットアップを押したときに TRUE で入る）
4. 集計表のメニュー「表示 > 隠しているシート」から「集計表の設定」を開き、ひな型のID（ひな型のスプレッドシートの URL でもよい）、新しいテストのフォルダのID、保管用のフォルダのIDを入れる
5. 今の本番（10/23 のテスト）は、その時点の仕組みのまま残す。送り先をひな型に変えたあとは、本番へは送らない（直す必要が出たときだけ、本番のスクリプトIDの `.clasp.json` に一時的に替えて送り、終わったらひな型に戻す）

#### 新しいテストを作る（先生）

1. 集計表のメニュー「集計表 > 新しいテストを作る」を押し、聞かれる順にテスト名・科目・実施日（2026/11/6 のように）を入れる
2. ひな型に前のテストの記録（回答・待ち行列・フォームの記録・保管の印）が残っていれば、理由が出て止まる。導入担当者にひな型を空に戻してもらう
3. 問題なければ、新しいテストのフォルダに「科目 実施日 テスト名」という名前のスプレッドシートができる。名簿シート（クラス・No.・氏名・呼び名）には集計表の名簿が写り（No. は学生番号、呼び名は空欄）、テスト一覧に1行足される
4. 出てきた URL から新しいスプレッドシートを開き、メニュー「AI Grader > 初期セットアップ」を押して許可する。そのあと試験作成シートで問題を作る

名簿を直すときは、集計表の名簿を直してから新しいテストを作ります（作り終えたテストの名簿は変わりません）。

#### 保管する（先生。返却が終わったテスト）

返却が終わったテストは「保管する」で片づけます。そのテストの1分ごとの自動処理が止まり、フォームが閉じ、保管用のフォルダへ移ります（ADR 0010）。2回押して済ませます。

1. テスト一覧シートで、保管するテストの行を選び、メニュー「集計表 > 保管する」を押す。そのテストの全版のフォームの受付が閉じ、保管の状態が「停止待ち」になる
2. 最後の回答の採点が終わるのを待ってから、同じ行を選んでもう一度「保管する」を押す。次のものが残っていれば、保管されずに一覧で出る。それぞれ書いてある操作をしてから、もう一度押す
   - 採点が確定していない回答（テストのスプレッドシートで「手動採点を反映」などで確定する）
   - 集計表に取り込まれていない確定済みの回答（「取り込む」を押す）
   - 未解決の要確認（要確認シートで判断を書き、「取り込む」を押す）
   - 待ち行列に採点を待つ回答（1分ほど待つ）
3. 残りが無ければ、テストに保管の印が付く。テスト側が自動処理を止めるまで1分ほどかかるので、「まだ止まっていません」と出たら、1分ほどしてからもう一度押す
4. 止まっていれば、テストのスプレッドシートと全版のフォームが保管用のフォルダ（集計表の設定の「保管用のフォルダのID」）へ移り、保管の状態が「保管済み」になって、実施中の印が外れる。以後は押しても「保管済みです」と出るだけ

保管したテストの点数は、成績シートに残り続けます。取り込みのときは、保管済みのテストは開き直さず、それまでの取り込み記録をそのまま使います。

### 練習の受付ページ（使う場合だけ）

学生が手順を何度でも体験できる、本番とは別の受付ページとフォームです。作り方と動作の確認は `practice/README.md` を見てください。

### LLM 採点の準備（API を使う場合だけ。既定では不要）

1. Anthropic で**この仕組み専用の API キー**を作り、提供元の画面で月額の上限を設ける
2. Apps Script の「プロジェクトの設定 > スクリプト プロパティ」に `ANTHROPIC_API_KEY` として登録する（シートやリポジトリには書かない）
3. Settings シートの `LLM_MODEL` に使うモデル名を入れる
4. Apps Script エディタで `diagnoseAnthropic` を選んで実行し、「接続に成功しました」と出ることを確かめる

注意:

- シートの編集者は Apps Script も開けるため、キーを読める可能性があります。シートの編集権限は必要な教員だけに限ってください
- `appsscript.json` の `urlFetchWhitelist` で、通信先を `https://api.anthropic.com/` だけに限っています。他社の提供元を足すときは、ここへの追加が必要です

- 【未確認】新しいテストの成績の公開の初期値。先生がフォームの設定で「後で手動で公開」にする

- 【未確認】回答先に「フォームの回答 N」シートが版ごとに増える（扱いを決める）

採点:

- 【確認済み 2026-10-20】学生が送信すると、1分以内に Queue に job が1件できる（同じ回答で増えない）
- 【確認済み 2026-10-20】AUTO の問題が採点され、Results に「回答×問題」で1行ずつ入る
- 【未確認】回答に `=1+1` のような文字を入れても、Results では文字のまま表示される
- 【確認済み 2026-10-20】MANUAL の問題が残る回答は、Queue が REVIEW_REQUIRED のままになる
- 【未確認】「採点を今すぐ進める」を連続で押しても二重に採点されない
- 【未確認】`diagnoseAnthropic` が成功する
- 【未確認】LLM の問題が採点され、Results に提供元・モデル・版・理由・信頼度が入る
- 【確認済み 2026-10-20】通信が失敗した問題は REVIEW_REQUIRED になり、0点にならない（キー未設定の失敗で、再試行になり0点にならないことを確認。最終的な要確認への切り替えは未確認）
- 【未確認】60人規模の同時送信で、実行時間やUrlFetchの1日の上限に収まる
- 【未確認】信頼度の閾値 0.80 で、要確認がどの程度出るか（実際の答案で確かめる）

フォームへの書き戻しと確定:

- 【確認済み 2026-10-20】全問が確定した回答だけ、フォームの採点結果に点数が反映される（MANUAL・要確認が残る回答は反映されない）（フォームの回答一覧で、記述式を手動採点した回答の合計が 13/20 になることを確認。Q001 のような短答の点は、書き戻しでしか付かない）
- 【確認済み 2026-10-20】`manual_score` に点を入れて「手動採点を反映」を実行すると、その回答が確定してフォームへ反映される
- 【確認済み 2026-10-20】反映によって Queue に新しい job が増えない
- 【未確認】Results の行を選んで「選択回答を再採点」を実行すると、行が更新され（増えない）、入力済みの `manual_score` は残る

- 【未確認】システム診断が Control に結果を出す
- 【未確認】Logs に API キーや認可ヘッダが出ていない

## 既知の制約

- 回答が残っている旧版の採点が終わるまでは、Questions の配点・正答を大きく変えないでください（採点は現在の Questions を使います）
- 回答後の編集は許可していません（フォームの設定）
- 部分点は v1 にありません（チェックボックスは全部合えば満点、それ以外は0点）
- LLM 提供元は Anthropic のみ実装済みです（OpenAI・Gemini は未実装。選ぶと設定の確認でエラーになります）
- LLM の点数は整数のみです
- correct_answer やルーブリックを変えても、フォームの版は上がりません。回答が残っている間は変更しないでください

# Matt2

Claude Code で開発を進めるための**テンプレート**です。ここから複製して、新しいプロジェクトを始めます。
製品のコードは入っていません。入っているのは「進め方の仕組み」だけです。

## 複製したら最初にすること

会話を開いて、そのまま話しかけてください。何も打たなくても、AI が
「前回の続き・いまの状態・最初の一手」を報告します。

そのうえで、次の1つだけ打てば始まります。

```
/grill-with-docs
```

AI が質問を重ねて、作りたいものの曖昧な部分を潰します。答えるだけで構いません。
決まった用語は `CONTEXT.md` に、重要な判断の理由は `docs/adr/` に書き残されるので、
次の会話にも引き継がれます。

相談が済んだら、次を打てば残りは任せられます。

```
/conduct
```

計画書づくりから実装・確認・修正までを、役割表（`.claude/router/roles.txt`）に従って
Claude・GPT（Codex）・Gemini に振り分けて進めます。あなたが関わるのは、途中確認と最終確認で
GO / NG を返すときだけです。3社の道具を使うには、先に一度だけ
[Windows での初回準備](docs/setup-windows.md) を済ませてください（済ませていなくても、Claude だけで進みます）。

複製した直後の最初の会話では、ひな型自身の作業日誌が自動で片づき、引き継ぎメモが白紙になります。

その後、この `README.md` の冒頭をプロジェクトの説明に書き換えてください。

## 覚えるのはこの3つだけ

| 打つもの | 何が起きるか |
| --- | --- |
| `s` | 前回の続き・いまの状態・最初の一手を報告します（開始時は自動でも出ます） |
| `f` | 環境を破棄しても大丈夫な状態まで片づけ、終了して良いかを報告します |
| `/next-step` | いまどこにいて、次に何を打てばいいかを1つだけ提示します |

コマンドを覚える必要はありません。「〇〇を作りたい」と伝えるだけでも、実装前に自動で案内が入ります。

## 入っているもの

- `.claude/skills/` に [mattpocock/skills](https://github.com/mattpocock/skills) を 12 個インストール
  （`npx skills add mattpocock/skills`、`skills-lock.json` でバージョン固定）
  - ユーザー起動（このうち案内で使うもの）: `grill-with-docs` / `to-spec` / `to-tickets` / `implement` / `improve-codebase-architecture` / `setup-matt-pocock-skills`
  - モデル起動: `grilling` / `domain-modeling` / `codebase-design` / `tdd` / `code-review`
- `.claude/skills/s/`, `.claude/skills/f/`, `.claude/skills/next-step/`: この置き場所独自の案内役と儀式
- `.claude/skills/conduct/`: 指揮の案内役。相談の後の全段階を、役割表に従って3社の道具に振り分けて進める
- `.claude/router/`: 振り分け役（`route.sh`）と役割表（`roles.txt`）。モデルの乗り換えは役割表の書き換えだけで行う
- `.claude/hooks/template-cleanup.sh`: 片づけ役。複製先の最初の会話で、ひな型の作業日誌を片づける
- `.template/`: ひな型自身の記録（用語集・決めた理由など）。複製先では自動で消える
- `tests/`: 振り分け役と片づけ役の検査。直したときに `sh tests/route.test.sh` と `sh tests/template-cleanup.test.sh` を流す
- `docs/setup-windows.md`: Windows での初回準備の手引き
- `.claude/settings.json`: 会話開始時に `docs/agents/flow-map.md` を読み込む仕組み
- `docs/agents/flow-map.md`: 進め方と、説明の書き方のルール
- `docs/agents/handover.md`: 会話をまたぐ引き継ぎメモ。区切りごとに自動で追記されます
- `AGENTS.md`: 開発フローの全体像
- `docs/agents/issue-tracker.md`: 作業指示書の置き場所は GitHub Issues
- `docs/agents/domain.md`: 用語集は `CONTEXT.md`、判断の記録は `docs/adr/`

## フロー全体

- 新規開発・機能追加: `/grill-with-docs` → `/conduct`（あとは途中確認と最終確認で GO / NG を返すだけ）
- 手で1段ずつ進める場合: `/grill-with-docs` → 必要に応じて `/to-spec` → `/to-tickets` → `/implement`
- 設計改善: `/improve-codebase-architecture` → 候補を選択 → `/grill-with-docs` または `/codebase-design` → 以下同じ

`/implement` は `/tdd` で RED → GREEN を繰り返し、最後に `/code-review` を実行します。
詳細は [AGENTS.md](./AGENTS.md) の「Development flow」を参照してください。
