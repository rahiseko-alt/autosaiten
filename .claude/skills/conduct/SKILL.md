# conduct — 指揮の案内役

利用者は非エンジニア。関わるのは **人の確認点** の3回だけ（最初の相談・途中確認・最終確認）。
最初の相談は `/grill-with-docs` が済ませている。この案内役は、その後の全段階を人の操作なしで進める。

用語はひな型の用語集に従う（指揮役・担当・役割・役割表・振り分け役・自動モード・単独モード・
後回しの確認・人の確認点）。ひな型専用フォルダが片づいた複製先でも意味が通るよう、ここで使う語は
この文書の中で完結させる。

## 絶対規則

- **時刻を決めた見回りを予約しない。** 利用者の返事待ち、自動チェック待ちの間も、`send_later`・
  `create_trigger`・`/loop`・`ScheduleWakeup` は使わない。返事や知らせが届いたときに動けば足りる。
- **利用者に途中で選択を求めない。** 下の各段階で使う部品（`/to-spec`・`/to-tickets` など）には
  利用者に確かめる手順があるが、利用者は人の確認点以外の判断を任せている。ここでは自分で決めて進め、
  決めた内容は計画書・作業指示に残す。
- **mattpocock/skills 由来の部品は書き換えない。** 中身を読んで、その手順に従うだけにする
  （利用者専用の部品は呼び出せないため、`.claude/skills/<名前>/SKILL.md` を読んで同じことをする）。
- 決めた理由（`docs/adr/`。ひな型そのものを直しているときは `.template/docs/adr/` も）があれば、
  確認役に渡す依頼文に**そのまま貼り付ける**。食い違いは違反として扱わせる。
- 利用者への報告はすべて `docs/agents/flow-map.md`「説明の書き方」の3ブロック（結論／理由／次）で書く。

## 振り分け役の使い方

```sh
printf '%s' "依頼文" | sh .claude/router/route.sh <役割名>   # 仕事をさせる
sh .claude/router/route.sh --check                          # モード判定（利用枠を使わない）
```

返ってくる見出し行:

- `assignee: 道具:モデル` … 実際に仕事をした担当
- `solo: yes|no` … 他社を全部飛ばして Claude に落ちたら `yes`
- `skipped: 道具:モデル (理由)` … 飛ばした担当と理由（not-installed / not-logged-in / usage-limit / error）
- `---` の後が担当の答え

役割名は `.claude/router/roles.txt` の1列目。担当の差し替えはその表だけで行う。

依頼文は、担当がこの会話を知らない前提で書く。目的、読むべき文書（計画書・作業指示の本文を貼る）、
やってほしいこと、返してほしい形を必ず含める。

## 手順

### 0. 始める前に

1. `sh .claude/router/route.sh --check` を実行し、モードを3ブロックで伝える。例:
   - **結論**: 自動モードで進めます。／単独モードで進めます。
   - **理由**: 他社の道具（Codex・Gemini）が使えるので、役割表どおりに振り分けます。／
     他社の道具が使えないので、Claude が全役割を代行します。他社による確認は後でまとめて行います。
   - **次**: 計画書づくりから始めます。次に声をかけるのは途中確認のときです。
   （`--check` はログインの有無しか見ない。使用上限は実際に頼んだときに振り分け役が見分けて、代わりの担当へ回す。）
2. 自動モードなら、**後回しの確認**を先に片づける。タイトルが `【後回しの確認】` で始まる開いている作業指示を
   すべて読み、それぞれに書かれた役割名で振り分け役に確認させ、結果を作業指示に書き込んで閉じる。
   指摘があれば、下の「7. 修正」と同じ扱いで直す。
3. 作業用の枝を用意する。作業環境が使う枝を指定していればそれを使い、無ければ本流の最新から
   `conduct/<短い英語の名前>` を作る。以降の記録はすべてこの枝に送る。最初に送ったときに、
   この枝の提出物を**下書き**として作る（最終確認の GO で本流へ取り込む対象になる）。

### 1. 計画書

`.claude/skills/to-spec/SKILL.md` を読み、その手順で計画書を書いて作業指示として登録する。
検査の入口の確認は利用者に聞かず、自分で決めて計画書に書く。

### 2. 設計の確認

計画書の本文を渡し、`design-review-1` と `design-review-2` に**別々に**確認させる（互いの答えは見せない）。
依頼文には「抜け・矛盾・危険・もっと単純な案」を挙げるよう書く。
2つの答えを `design` に渡して計画書を直させ、直した計画書で作業指示を更新する。

### 3. 小分け

`.claude/skills/to-tickets/SKILL.md` を読み、その手順で作業指示に小分けして登録する。
分け方の確認は利用者に聞かず、自分で決める。

### 4. 実装

先に済ませる作業が無いものから順に、1件ずつ進める。

1. 作業指示を `implement-light`（1〜2か所の素直な変更）か `implement-complex`（複数箇所・設計判断を含む）に
   振り分ける。迷ったら `implement-complex`。
2. 依頼文には作業指示の本文、この置き場所の検査の流し方、「先に失敗する検査を書き、通す」ことを入れる。
3. 担当が終えたら、指揮役が自分で検査を流す。落ちていれば、落ちた内容を添えて同じ役割にもう一度頼む。
   2回続けて落ちたら `implement-complex`、それでも駄目なら `fix-design` に回す。
4. 通ったら作業用の枝に記録して送る。作業指示を閉じる。

最初に「動くもの」が1つできた時点で、**5. 途中確認**を挟む。

### 5. 途中確認（人の確認点）

最初に、利用者が触って意味のある「動くもの」ができたら1回だけ行う。

1. `run` の部品で起動し、動いている様子の画面写真を撮る。作るものによっては、触れる画面へのリンクも用意する。
2. 利用者に送る中身は次の2つだけにする。
   - 3ブロックの説明。専門用語は使わない
     - **結論**: 何ができたか
     - **理由**: どう動くか（画面写真のどこを見ればよいか）
     - **次**: 「このまま進めてよければ GO、違えば NG と一言の理由をお返しください。」
   - 画面写真（会話に添付する）。あればリンク
3. 送ったら**止まる**。
4. GO なら 4. 実装に戻る。NG なら、理由を作業指示に書き足して直し、もう一度 5. 途中確認をやり直す。

### 6. 仕上げの確認

全作業指示が閉じたら、本流との差分全体と計画書を渡し、`final-review-1` と `final-review-2` に
**別々に**確認させる。依頼文には「計画書との食い違い・不具合・危険・決めた理由との矛盾」を、
重さ（直さないと出せない／直した方がよい／好み）つきで挙げるよう書く。

### 7. 修正

仕上げの確認の指摘のうち、「直さないと出せない」「直した方がよい」を直す。

- 1〜2か所の素直な修正 → `fix-light`
- 複数箇所にまたがる修正 → `fix-complex`
- 設計の変更が要る修正 → `fix-design`

直したら検査を流し、記録して送る。設計の変更をした場合は 6. 仕上げの確認をもう一度行う。

### 8. 最終確認（人の確認点）

5. 途中確認と同じ形（3ブロックの説明＋画面写真、あればリンク）で、完成したものを送って**止まる**。

- **GO**: 作業用の枝の提出物を下書きから正式な提出に切り替え、自動チェックが通っていることを確かめてから
  本流へ取り込む（`gh` が無ければ GitHub の MCP ツールで同じことをする）。自動チェックが落ちていれば直してから
  取り込む。取り込めたら3ブロックで伝え、引き継ぎメモに記録する。
- **NG**: 一言の理由を作業指示にして 4. 実装から直し、6. 仕上げの確認を経て、もう一度最終確認を行う。

## 単独モード・代わりの担当のとき

- 振り分け役の答えに `skipped:` があれば（`solo` が yes でも no でも）、代わりの担当で進んだということ。
  その段階が終わった後の報告の**理由**に「〇〇は使用上限のため、代わりに△△が担当しました」と一言入れる。
  途中で止まって報告はしない。
- `solo: yes` で、それが**確認の役割**（`design-review-*`・`final-review-*`）なら、**後回しの確認**として
  作業指示を1件登録する。
  - タイトル: `【後回しの確認】<役割名>: <確認した対象>`（目印はこのタイトル。ラベルの有無に頼らない）
  - ラベル: `deferred-review` を付けられれば付ける（無ければ作る。作れなければ付けずに進める）
  - 本文: 役割名、確認した対象（計画書の作業指示番号、または確認時点の記録の識別子）、
    Claude が代行した確認の要点
  - 作業は止めずに先へ進む。次に自動モードで始めたとき、0. の手順でまとめて確認する。
- 振り分け役が失敗した（全担当が使えない）ときは、その理由を3ブロックで伝え、
  使用上限なら上限が戻った後の会話で続きから再開する。見回りは予約しない。

## 記録

- 計画書の登録後、小分けの登録後、途中確認の GO 後、最終確認の GO 後に、引き継ぎメモへ1件ずつ足す
  （書式は `docs/agents/flow-map.md`「引き継ぎメモ」）。
- 「次にやること」には、どの段階のどの作業指示から再開するかを書く。
